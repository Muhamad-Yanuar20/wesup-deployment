## Database deployment

The additional migration is `20260930211221_payment_clarity_capacity_opening.sql`. Previously applied migrations were not rewritten. Before application, a complete private JSON backup of 33 public tables, definitions and migration history was verified; SHA-256 **bd93d64b1fd84ff04dec93d0f3c860d381ded6cd0c42df6d4144af094c4f0402**. A transaction, advisory lock and before/after fingerprints checked existing order amounts, quantities and promised timelines. Application succeeded, then the active REST relation/schema preflight passed and database types were regenerated from the active PostgreSQL catalog.

Existing v2 rows default to `fixed_cutoff`; only new publication opts into `capacity_or_cutoff`. Legacy v1 behavior remains. Full-capacity join closes, locks prices/volume, issues invoices and establishes the effective 24-hour window in the same database transaction. Original timestamps remain stored. Redis is resynchronized to the locked database quantity, and join/withdraw share lock ordering. The existing remote late-payment refund handling was preserved.

Before deployment, [rollback-only live migration validation](evidence/payment-clarity/migration-validation.json) exercised new capacity closure, fixed-cutoff preservation, base/discount price distinction, withdrawal and same-identity rejoin. The SQL replay harness separately exercises all migrations and lifecycle authorities, including replacement consent, repeated lateness, wrong/reused pickup credentials, escrow, partial emergency cancellation and pending-provider protection. It distinguishes a newly published offer from a historical fixed-cutoff fixture rather than changing an immutable policy.

The live schema regression detected historical extra dispute enum values already present remotely. These are now represented explicitly as deployed extensions in the schema contract; no remote enum or customer data was removed.

Automatic checking has a four-request budget per attempt and a 15-second interval; manual checking remains. Component prop refresh does not reset that budget. No cron was added.

Refund remains an admin transfer workflow; `refund_pending` does not mean money has already returned to the bank account. PRD updates remain private and unstaged.
